## О компании «Тёплый дом»

«Тёплый дом» — небольшая компания, которая организует удалённое управление отоплением в доме. Недавно компания выиграла тендер и получила заказ на создание экосистемы умных посёлков на территории нескольких регионов страны.

**Текущее состояние:**
- Монолитное приложение на **Go** с **PostgreSQL**
- 100 веб-клиентов, 100 модулей управления отоплением
- Датчики и реле установлены только в половине домов, желающих подключиться
- Подключение датчиков требует выезда специалиста
- Всё синхронно: никаких асинхронных вызовов, микросервисов, реактивного взаимодействия

**Целевая модель:** SaaS самообслуживание
- Пользователь сам подключает устройства, настраивает сценарии, просматривает телеметрию
- Управление: отопление, свет, ворота, наблюдение, неизвестные будущие устройства
- Поддержка устройств партнёров по стандартным протоколам
- Модульные комплекты для удобной покупки и подключения

**Лэндскейп компании:**
| Команда | Кол-во | Задачи |
|---------|--------|--------|
| Разработчики | 5 | Рефакторинг, разделение монолита на микросервисы |
| QA | 3 | Тестирование новой системы |
| Обслуживание клиентов | 10 | Поддержка пользователей новой системы |
| Продажи и маркетинг | 5 | Продвижение модульных комплектов |

# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением (единственная текущая функция):**

- Пользователи могут удалённо включать и выключать отопление в отдельных комнатах.
- Пользователи могут устанавливать целевую температуру для каждого устройства.
- Пользователи могут переключать режимы работы: economy, comfort, night.
- Система поддерживает проверку бизнес-правил перед выполнением команды.
- Данные о температуре получаются по запросу от сервера к датчику (pull).
- Каждая установка требует выезда специалиста по подключению.
- Пользователь не может самостоятельно подключить свой датчик.

**Что отсутствует (по целевым требованиям):**
- Управление освещением
- Управление автоматическими воротами
- Удалённое наблюдение
- Самообслуживание пользователей
- Поддержка устройств партнёров
- Программирование сценариев работы
- Модульные комплекты

### 2. Анализ архитектуры монолитного приложения

**Стек технологий:**

| Компонент | Технология |
|-----------|-----------|
| Язык | Go |
| HTTP-фреймворк | Gin |
| База данных | PostgreSQL 16 |
| Драйвер БД | pgx/v5 |
| Коммуникация | Только синхронная (HTTP) |

**Структура приложения:**
- `main.go` — точка входа, инициализация соединений и роутинг
- `handlers/` — обработчики HTTP-запросов (SensorHandler)
- `services/` — бизнес-логика (TemperatureService)
- `models/` — структуры данных (Sensor)
- `db/` — работа с базой данных

**Взаимодействие с внешними системами:**
- Опрос датчиков температуры через HTTP (TemperatureService → внешний API)
- Пользовательский доступ через HTTPS
- Все вызовы синхронные — сервер ждёт ответа от датчика

**Сильные стороны монолита (для текущего масштаба):**
- Простота разработки и развёртывания
- Отсутствие сетевых задержек между компонентами
- Простое тестирование
- Достаточно для 100 клиентов

### 3. Определение доменов и границы контекстов

Исходя из целевых требований (SaaS, много устройств, партнёры), выделены 4 домена (bounded contexts):

| Домен | Описание | Ключевые сущности |
|-------|----------|-------------------|
| **Управление отоплением (Heating Control)** | Вкл/выкл, температура, режимы, команды устройствам | Device, DeviceState, HeatingMode |
| **Мониторинг температуры (Temperature Monitoring)** | Опрос датчиков, сохранение показаний, проверка порогов | TelemetryData, Sensor |
| **Уведомления (Notifications)** | Формирование и отправка уведомлений (email, push) | NotificationSetting, NotificationLog |
| **Учёт пользователей (Users)** | Регистрация, аутентификация, роли, права доступа | User, UserHouse |

**Границы контекстов (взаимодействия):**
- Heating Control → Temperature Monitoring: запрос текущей температуры
- Temperature Monitoring → Notifications: триггер при падении температуры
- Heating Control → Notifications: триггер при включении/выключении
- Users → Heating Control: проверка прав доступа (роль)

**Перспектива:** При расширении функционала (свет, ворота, наблюдение) домен Heating Control станет обобщённым «Device Management», а к мониторингу добавятся новые типы данных.

### 4. Проблемы монолитного решения

- **Бизнес не масштабируется:** Компания выиграла тендер на несколько регионов, но монолит не позволяет быстро добавлять новые модули (свет, ворота, камеры). Каждое добавление — изменение и пересборка всего приложения.
- **Отсутствие самообслуживания:** Пользователь не может самостоятельно подключить датчик. Каждый выезд специалиста — стоимость для компании. Микросервисная архитектура позволит выделить модуль «Onboarding» и сделать подключение автоматическим.
- **Разный масштаб доменов:** Мониторинг генерирует большой поток данных (телеметрия от сотен устройств), а управление пользователями — редкие операции. Монолит масштабируется целиком — расточительно.
- **Риск каскадных отказов:** Сбой в любом модуле валит всё приложение. Для SaaS-системы это критично — пользователи теряют доступ к управлению домом.
- **Один язык для всего:** Монолит на Go. Для будущих задач (ML-прогнозы потребления энергии, аналитика) удобнее Python. Микросервисы позволяют выбрать оптимальный язык для каждой задачи.
- **Единая БД:** Все домены делят одну PostgreSQL. Рост телеметрии = нагрузка на все запросы.
- **Команда из 5 разработчиков:** При работе над одним кодом неизбежны конфликты и блокировки. Разделение на микросервисы позволяет разбить команду по доменам.

# Задание 2. Проектирование микросервисной архитектуры

## Диаграмма контейнеров (Containers)

[Диаграмма контейнеров (To-Be)](./to_be_container.puml)

**Микросервисы целевой системы:**

| Микросервис | Назначение | БД |
|-------------|-----------|-----|
| **API Gateway** | Маршрутизация, аутентификация, rate limiting | — |
| **Heating Control Service** | Управление отоплением: команды, состояния, режимы | Heating DB |
| **Temperature Monitoring Service** | Опрос датчиков, хранение показаний, пороги | Monitoring DB |
| **Notification Service** | Email, push-уведомления, история | Notification DB |
| **User Service** | Регистрация, JWT, роли, права | User DB |
| **Device Registration Service** | Регистрация устройств, onboarding | Device DB |

**Инфраструктура:**
- **Message Broker (RabbitMQ/Kafka)** — асинхронная коммуникация между сервисами
- **Внешние провайдеры:** Email Provider (SMTP), Push Provider (Firebase/APNS)

**Принципы:**
- Database-per-Service: каждый микросервис — своя БД
- Синхронное взаимодействие через REST API
- Асинхронное через Message Broker
- Gateway — единственная точка входа

## Диаграмма компонентов (Components)

[Диаграмма компонентов Heating Control](./to_be_component.puml)

**Компоненты Heating Control Service:**
- **API Controller** — принимает HTTP-запросы от API Gateway
- **Command Handler** — бизнес-логика команд (вкл/выкл, температура)
- **Device State Manager** — управление состоянием, проверка бизнес-правил
- **Event Publisher** — публикация событий в Message Broker
- **External Clients** — HTTP-клиенты для Temperature Monitoring и Device Registration

## Диаграмма кода (Code)

[Диаграмма последовательности: Включение отопления](./to_be_code.puml)

**Сценарий «Пользователь включает отопление»:**
1. Пользователь → API Gateway: `POST /heatings/{id}/turn-on`
2. Gateway → User Service: проверка прав (JWT, роль)
3. Gateway → Heating Control: `POST /devices/{id}/commands`
4. Heating → Device Registration: данные об устройстве
5. Heating → Temperature Monitoring: текущая температура
6. Heating: бизнес-правила → изменение состояния
7. Heating → Broker: `publish(HeatingToggled)`
8. Broker → Notification Service → email/push пользователю

# Задание 3. Разработка ER-диаграммы

[ER-диаграмма](./to_be_er.puml)

**Сущности и связи:**

| Сущность | Описание | Связи |
|----------|----------|-------|
| **User** | Пользователь системы (SaaS) | 1→M UserHouse, 1→M NotificationSetting, 1→M NotificationLog |
| **House** | Дом/объект в посёлке | 1→M UserHouse, 1→M Device |
| **UserHouse** | Связь пользователь-дом с ролью | M→1 User, M→1 House |
| **DeviceType** | Тип устройства (термостат, датчик, реле) | 1→M Device |
| **Device** | Установленное устройство | 1→1 DeviceState, 1→M Module, 1→M TelemetryData |
| **DeviceState** | Текущее состояние устройства | 1→1 Device, M→1 HeatingMode |
| **HeatingMode** | Режим (economy/comfort/night) | 1→M DeviceState |
| **Module** | Модуль устройства (свет, ворота) | 1→M Device |
| **TelemetryData** | Показание телеметрии | M→1 Device |
| **NotificationSetting** | Настройки уведомлений | M→1 User |
| **NotificationLog** | История уведомлений | M→1 User |

**Ключевые решения:**
- UUID для всех PK (децентрализованная генерация в микросервисах)
- User↔House через UserHouse (many-to-many с ролью: владелец, арендатор, гость)
- DeviceState — 1:1 с Device (обновляется, не дублируется)
- TelemetryData — 1:M с Device (каждое измерение — новая строка)
- Module позволяет расширять устройства (свет, ворота, камеры) без изменения таблицы Device

# Задание 4. Создание и документирование API

## 1. Тип API

**REST API (OpenAPI 3.0) — синхронное взаимодействие**

Операции управления требуют немедленного ответа: включение/выключение отопления, установка температуры, запрос состояния, аутентификация. Пользователь и другие микросервисы ждут подтверждения.

**AsyncAPI (2.6) — асинхронное взаимодействие**

Уведомления и события не требуют немедленной доставки. События (`HeatingToggled`, `TemperatureDrop`, `NewReading`) публикуются в Message Broker, подписчики обрабатывают в своём ритме.

## 2. Документация API

**Полная спецификация:** [docs/api-specification.md](./docs/api-specification.md)

**OpenAPI 3.0 (YAML):** [docs/api-specification.yaml](./docs/api-specification.yaml)

**Краткая документация:** [docs/api-documentation.md](./docs/api-documentation.md)

### REST-эндпоинты

| # | Метод | Путь | Микросервис | Описание |
|---|-------|------|-------------|----------|
| 1 | `POST` | `/auth/login` | User Service | Аутентификация, JWT |
| 2 | `POST` | `/devices` | Device Registration | Регистрация устройства |
| 3 | `GET` | `/devices/{id}/state` | Heating Control | Состояние устройства |
| 4 | `POST` | `/devices/{id}/commands` | Heating Control | Команда (вкл/выкл/температура) |
| 5 | `GET` | `/devices/{id}/telemetry/current` | Temperature Monitoring | Текущая температура |

### Асинхронные события (AsyncAPI)

| Событие | Topic | Публикатор | Подписчики |
|---------|-------|------------|------------|
| `HeatingToggled` | `heating.toggled` | Heating Control | Notification |
| `TemperatureSet` | `heating.temperature_set` | Heating Control | Notification |
| `TemperatureDrop` | `temperature.drop` | Temperature Monitoring | Notification, Heating Control |
| `NewReading` | `temperature.new_reading` | Temperature Monitoring | Notification |

# ✅ Задание 6. Разработка MVP

Созданы 2 микросервиса, интегрированных с монолитом для плавного перехода к микросервисной архитектуре.

## 1. Device Service — Python / Flask (порт 8082)

CRUD-управление устройствами. БД: SQLite (volume).

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/devices` | Список устройств |
| `POST` | `/devices` | Создать устройство |
| `PUT` | `/devices/<id>` | Обновить |
| `DELETE` | `/devices/<id>` | Удалить |
| `GET` | `/devices/sensor/<sensor_id>` | По sensor_id |

## 2. Telemetry Service — Java / Spring Boot (порт 8083)

Хранение и запрос показаний телеметрии. БД: H2 (file-based, volume).

| Метод | Путь | Описание |
|-------|------|----------|
| `POST` | `/telemetry` | Записать показание |
| `GET` | `/telemetry` | Все показания |
| `GET` | `/telemetry/sensor/{id}/latest` | Последнее показание |

## 3. Интеграция с монолитом (Go)

Монолит через HTTP-клиенты (`device_service.go`, `telemetry_client.go`) при каждом CRUD-действии синхронизирует данные с микросервисами. Ошибки не блокируют основной ответ.

## 4. Запуск

```bash
cd apps
docker-compose up --build
```

| Сервис | Язык | Порт | БД |
|--------|------|------|-----|
| `postgres` | — | 5432 | PostgreSQL |
| `temperature-api` | Go | 8081 | — |
| `device-service` | Python | 8082 | SQLite |
| `telemetry-service` | Java | 8083 | H2 |
| `app` (монолит) | Go | 8080 | PostgreSQL |

**Разные языки (Go, Python, Java)** — демонстрация ключевого преимущества микросервисов: каждый сервис использует оптимальный стек, что необходимо для масштабирования компании «Тёплый дом» на несколько регионов.
